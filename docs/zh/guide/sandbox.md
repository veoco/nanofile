# 沙盒

所有解析用户提供内容的功能都在独立子进程中运行，带有内存上限、CPU 上限与墙钟超时，不在服务器进程内：

- 搜索索引的文档正文提取，
- 图片缩略图，
- 媒体缩略图（经 `ffmpeg`），
- EXIF 与头像处理。

子进程在读取请求之前先自我约束并自我限制，然后打印它实际建立的保护。服务器按这份报告决策，而不是按它提出的要求。

## 资源边界是强制项

资源边界是唯一任何设置都不能放弃的一项。建立不了它的子进程会被父子两侧同时拒绝，因为解析炸弹或死循环正是这套机制要防的失败。一台连资源边界都建立不了的主机，这些功能一律不运行。

这些功能解析的东西全是纯 Rust（`lopdf`、`office_oxide`、`zip`、`image`、`kamadak-exif`），唯一会启动的外部程序是媒体 helper。因此文件、网络与进程三层是刻意叠加的纵深防御，用来防解析器自身的漏洞，而不是维持服务器存活的那道边界。

## 管理后台的沙盒页

**沙盒**页面列出本机实际给出了什么：每个被实测的 profile 一个分组，每项保护一行，每个分组带一个状态徽章说明该 profile 是否在运行。页面不在它们之上再做总结——既没有"等级"，也没有结论句，因为两者都只是把徽章与行里已经写着的东西再说一遍。

每一行说明这一项是什么、是否就位、有多重要，以及缺了它意味着什么：

- **资源边界** —— 各平台都有内存与 CPU，Linux 与 macOS 上还包括句柄与文件大小。页面把它标为"必选"。
- **文件访问** —— 路径不可读也不可写。这一项把解析器挡在服务器用户的数据之外；它缺失时页面直接点名，而不会把其他层当作替代品。
- **网络访问** 与 **启动程序** —— 建立在"文件已隔离"之上的加固，永远不能替代文件层。

本平台固有的残余注在它们所削弱的那一项旁边：

- macOS 的解析器 profile 直接拒绝 `fork`，并把 `exec` 收窄到子进程自身的镜像。
- Windows 容器可读取它启动所需的系统目录；其 Job Object 约束内存与 CPU 时间，但没有句柄与文件大小的等价物。
- 媒体 worker 除 helper 本身外还被授予它所需的库。

## 媒体 worker

媒体 worker 有自己的一组分组，也是唯一按设计就列不全的一组。它的存在意义就是启动程序，而任何启动程序的方式都要先复制进程，因此"启动程序与进程"这一项对它不可能成立。页面写 **不适用**，而不是记成缺失。约束它的是文件层与时间限制，后者约束副本数。

- 在 Linux 与 macOS 上文件层按路径决定 `exec`：只放行 helper 与内核为它启动的解释器，绝不放行任何目录。
- 在 Windows 上容器并不限制可执行哪个可读程序，因此只有 Job Object 的进程数与超时能约束被攻陷的 helper。

媒体 profile 的"文件访问"一项带有自己的注记。helper 是带库的程序：它可以读取 helper 旁边的库文件（逐个文件授权）、系统库目录，以及在 macOS 上——**且仅当 helper 确实安装在该目录下时**——它链接的打包管理器目录（`/opt/homebrew`、`/usr/local`、`/opt/local`）。

在 Linux 上媒体子进程不得调用 `setsid`/`setpgid`，因此它复制出的副本无法脱离父进程杀掉的进程组。在 macOS 上没有任何机制拒绝这两个调用，副本可以脱离该进程组；剩下的唯一约束是每个副本自身的 CPU 上限与父进程的超时，而不是副本数量。

## 总开关

`[sandbox] enabled` 是总开关。关闭后：

- 上述功能一律不运行，
- 不会回退到服务器进程内解析，
- 关闭期间跳过的文档记为可重试状态，而不是对其字节下的结论，因此重新打开后会被重新索引。

资源边界之上的一切都由平台决定，而不是配置项。页面上每一行都来自真正被约束过的子进程，因此它无法宣称本机没有的保护。

## Windows

Windows 上的容器会被尝试，被拒绝时退回资源边界。AppContainer 是该平台唯一能补上文件与网络两项的机制，而创建它需要在注册表写入 profile，并在 worker 自身镜像上给出包访问权限。

一个约束自己所有子命令的主机沙盒（开发或 agent 环境）恰恰会拒绝这些，子进程随后死在加载器里且没有任何可诊断的信息。因此建不出容器的 Windows 启动会改为应用 Job Object、受限令牌与进程缓解策略并报告 `files=open`，并且在该进程内不再重复申请容器。两种情况下页面都会列出缺了什么。

## 媒体 helper

`storage.ffmpeg_path` 指定媒体 profile 可以执行的辅助程序。保存它会通过与总开关相同的钩子重新解析这份授权，因此下一次媒体请求执行的就是刚配置的二进制。

- 在 Windows 上，容器只会被授予 helper 的文件**以及它旁边的库文件**，绝不涉及目录。它的令牌保留了 `SeChangeNotifyPrivilege`，所以到达该文件的路径不会被检查；而在目录上写入 DACL 会把继承关系重新施加到其下所有对象上。
- helper 的标准流使用管道而不是空设备，因为容器可能拒绝打开该设备，而这种拒绝看起来就像"helper 起不来"。
- 如果 helper 只能在普通容器下运行——它的读权限来自 `ALL APPLICATION PACKAGES`，而更严格的容器变体会让访问检查忽略该 principal——媒体 profile 就改在普通容器里运行它：放弃该变体（报告与页面上记为 `lpac=off`），保留容器本身。
- 容器中可能需要放行 Landlock 系统调用，四项才能全部就位。

## 测了什么，没防什么

沙盒是在**使用它的地方**被测的，而不只是在描述它的地方。本项目交付的每个平台都跑完整的 Rust 测试套件，每个 profile 的报告只在一处断言。probe 会解析它携带的每一种结构化格式，把图片子进程的回复对照交给它的像素，并把整条媒体流水线端到端跑一遍。worker 完全起不来的机器上，头像上传、EXIF 读取与缩略图都必须拒绝，而不是退回服务器进程内解码。

机制与 probe 的细节见[沙盒内部](/zh/dev/sandbox)。

沙盒不防的东西不会被断言为成立：内核漏洞，以及以同一用户运行的其他进程。这些测试针对的是本服务自己建立的约束，而不是它下面的内核。
