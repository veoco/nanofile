# 监控

Nanofile 提供一个很小的就绪接口和一个任务控制台；它不自带 Prometheus 接口。本页讲该看什么、去哪里看。

**适合谁：** 以服务或容器方式运行 Nanofile 的人。**前置条件：** 服务器在运行，日志写到你能读到的地方。

## 健康检查

`GET /health` 是就绪检查。它返回 `200 OK`、空响应体和 `x-nanofile-generation` 头。可用于：

- 容器健康检查；
- 负载均衡或反向代理的上游检查；
- 重启后等待服务器回来的脚本。

每次就地**重启服务**都会改变 generation 头。管理后台的重启页正是靠它判断“回来的是新进程”，因为单纯的 200 分不清旧进程和新进程。健康检查只应要求 200，不应要求某个固定的 generation 值。

```bash
curl -fsS http://127.0.0.1:8082/health >/dev/null && echo ok
```

## 日志

`[logging]` 决定日志去哪、记多少：

| 键 | 作用 |
|---|---|
| `logging.level` | 日志级别 |
| `logging.file_enabled` | 写到文件而不是 stdout |
| `logging.file` | 日志文件路径 |
| `logging.max_file_size_mb` | 单个日志文件的上限 |
| `logging.max_backups` | 保留多少个旧文件 |

- 桌面（托盘）运行写文件，并把解析出的路径记进 `[logging] file`。
- 无头运行写 stdout；用 `journalctl -u nanofile -f` 或容器日志查看。
- Windows 服务写到二进制旁的 `nanofile.log`。

日志级别与文件上限在进程启动前就已决定。就地**重启服务**不会重新走这一步；只有停止再启动进程才会生效。

## 任务管理

**系统设置 → 任务管理**分为两页：

- **任务列表**先给出服务器负载（在途请求、运行中任务、排队任务、数据库连接、工作线程占用与活跃任务），然后才是运行本身：正在运行的作业，以及服务器真正做过的事。已完成列表只保留有内容可报的运行，因此“什么都没找到”的定时清理不会把它们淹没；可以按任务、按成功／失败筛选。
- **已注册的任务**列出本服务器注册的每一个作业与常驻服务，并按触发方式分组。每一行说明它什么时候运行、做什么，并用同样的右对齐列给出上次运行——从历史里读回来。展开一行能看到累计计数与运行策略：优先级、并发上限、超时、重试、是否等待服务器空闲、能以什么粒度中断、崩溃后会留下什么。

升级后想确认迁移类作业有没有跑完，看这里。失败的运行把作业自己的报错直接显示在行内，运行 ID、摘要与完整报错放在展开里。

## 负载与磁盘

- **任务管理 → 任务列表**顶部是服务器负载最直接的读数：在途请求、运行中任务、排队任务、数据库连接、工作线程占用与活跃任务。
- 左侧栏的空间用量条显示当前账号相对配额的用量。
- 数据目录会随着 `blocks/`、数据库、索引、缩略图和头像增长。看文件系统，不只看数据库：

```bash
df -h /opt/nanofile/data
du -sh /opt/nanofile/data/*
```

- 删除文件不会立刻释放块；垃圾回收要等 `gc.min_block_age_secs`，并且没有任何提交再引用该块。见[维护](/zh/guide/operate/maintenance)。
- 索引可以重建；`index/` 大了或不一致时可以删掉重建。`blocks/` 与 `nanofile.db` 不能重建。

## 备份校验

备份只有能恢复才算备份。保持定期执行并实测：

1. 按[备份、恢复与升级](/zh/guide/operate/backup-and-upgrade)执行备份。
2. 用同一个主密钥把它恢复到一个一次性的数据目录。
3. 在另一个端口启动恢复出来的实例，登录、下载一个文件，并对恢复出的块目录跑 `nanofile verify-blocks`。
4. 把日期和结果记在服务器之外，免得服务器丢了连备份历史也丢了。

## 建议告警项

- **`/health` 连续多次失败**。
- **任务失败反复出现**，尤其是升级后的迁移类作业。
- **磁盘用量**超过数据文件系统的 80%。
- **备份时间**超过计划允许的间隔。
- **反向代理证书过期**。
- **邮件队列**持续增长或卡在失败状态（如果启用了邮件）。
- **登录锁定或限流**突然增多，可能是撞库尝试。
